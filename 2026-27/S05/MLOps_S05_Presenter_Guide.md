### Slide 3 — What did the green tick check? *(minutes 4–6)*
**Point:** the pipeline is not magic: four named checks, run because someone pushed a change. **Say it like this:** harvest the chat for 90 seconds; read a few guesses aloud ("the code works", "the model is good"). ### Slide 4 — Why ML needs its own version of CI/CD *(minutes 6–8)*
**Point:** five differences from ordinary software, from the Google Cloud reading. **Say it like this:** one line each: the team (data scientists, not production engineers), development (experimental: the hard part is remembering what worked, last week's MLflow), testing (you test the data and the model, not only the code), deployment (you ship a pipeline that makes models, not one program), production (models decay as the world changes). The analogy: ordinary software is a **printed book**: once checked, it stays right. A model is a **weather forecast**: it was right this morning and may be wrong tomorrow without anyone touching it. **Land:** "Software breaks when someone changes it. A model breaks when the world changes." **Ask:** —

## CI, CD and the third letter: CT (5–8)

### Slide 5 — Divider *(minute 8)*
**Point:** the story of the block in one sentence. **Say it like this:** "Software has CI and CD. Machine learning adds a third letter, CT, because what we deliver is not a program but a pipeline that produces programs." **Land:** that sentence. **Ask:** —

### Slide 6 — CI, CD and CT, when the product is a model *(minutes 8–10)*
**Point:** each letter grows when the product is a model. **Say it like this:** **CI** (continuous integration): every change is checked automatically; for ML that means code *and* data. **CD** (continuous delivery): a checked change can reach production automatically; for ML what is delivered is a pipeline that deploys the prediction service. **CT** (continuous training): new, and only in ML: retrain and serve the model automatically when new data arrives or performance drops. Analogy for CT: a **bakery that bakes fresh bread every morning** with today's flour, instead of selling last month's loaf. Callback: the demo repository has CI and the start of CD; CT would be a schedule that runs it on new data. **Land:** "CI checks the change. CD ships it. CT keeps the model fresh." **Ask:** —

### Slide 7 — Three levels of maturity *(minutes 10–13)*
**Point:** where companies are, and where they should aim. **Say it like this:** **Level 0, manual**: a data scientist hands a model file to engineers; releases are rare; nobody watches it. **Level 1, automated pipeline**: new data triggers validate → train → evaluate → deploy by itself; the pipeline itself is still installed by hand. **Level 2, CI/CD for the pipeline**: even changes to the pipeline are tested and deployed automatically. Analogy: Level 0 is cooking every meal by hand; Level 1 is a bread machine that bakes by itself when you add flour; Level 2 is a factory that can also change its own recipe safely. Most companies are at Level 0; aim for Level 1. **Land:** "Most companies live at Level 0. The realistic goal is Level 1." **Ask:** "Where was NorthRetail?" (Level 0.) "And IberBank after the Friday hotfix?" (Level 0, with a laptop.)

### Slide 8 — The automated pipeline, stage by stage, and what starts it *(minutes 13–16)*
**Point:** six stages in a loop, and four kinds of trigger. **Say it like this:** walk the arrows once: experiment → pipeline CI (code pushed, built, tested) → pipeline CD (installed where it will run) → continuous training (runs on new data, the model goes to the registry) → model CD (the model is served) → monitoring (the numbers that can start the next run). Then the four triggers, one example each: a **push** (someone changed code), a **schedule** (every night at 2 a.m.), **new data** (an extract landed), a **performance signal** (accuracy fell below a line, Session 7). Like a **thermostat**: something measured crosses a line and the system acts by itself. **Land:** "Level 1 is the middle of this drawing running on its own." **Ask:** "Which trigger started the green tick you looked at?" (A push.)

## Tests, the demo, the artefact and the box (9–16)

### Slide 9 — Divider *(minute 16)*
**Point:** this block answers Forum 3, question 1, and contains the demo. **Say it like this:** "What does the pipeline check before anything reaches production? And what exactly does it ship?" **Land:** —. **Ask:** —

### Slide 10 — The ML test pyramid *(minutes 16–19)*
**Point:** three layers of tests, cheap and frequent at the bottom, expensive and rare at the top. **Say it like this:** **code tests**, every push, seconds: does each function do what it says, do the steps fit together? **Data tests**, every new extract: the right columns, sensible ranges, this week's data, roughly the usual number of rows, nothing that leaks the answer. **Model tests**, every candidate: a minimum score, not worse than the model in production, fair by segment, fast enough. Analogy: a **restaurant kitchen**: check the knives work every morning (code), inspect each delivery of ingredients (data), taste each dish before it leaves the kitchen (model). A failure at any layer stops the pipeline. **Land:** "Nothing reaches production without passing all three layers." **Ask:** "For a fraud model, which layer would catch a supplier sending amounts in cents instead of euros?" (Data tests: ranges.) This is Forum 3, Q1.

### Slide 11 — What a pipeline run looks like, then the demo *(minutes 19–26)*
**Point:** green means passed, red means stopped, and either way there is a record. **Say it like this:** read the three boxes: a green run (four steps passed), a red run (a new extract with a feature 70% empty stopped at "Validate data"), a record (who, which change, which step, the full log). Then **the demo, 6 minutes**, following `MLOps_S05_Demo_Script.md`: all runs → the green run → the pull request → the red run's log. Before you click: "I won't type anything; you'll just watch what the machine did by itself." If GitHub fails, open `demo/offline_fallback.html` and say the same words. **Land:** (after the demo) "It ran by itself, it stopped at the data test, and it left a record." **Ask:** —

### Slide 12 — What you just saw *(minutes 26–27)*
**Point:** three takeaways from the demo. **Say it like this:** **it ran by itself**: a push is the trigger, so nobody has to remember to run the tests and nobody can forget; **it stopped at the data test**: before training, before deployment, with a message a person can read; **it left a record**: when a regulator asks "what did you check before releasing?", this is the answer. Callback to Forum 2's misconception: "This is validation as a control: it can say no." **Land:** "The pipeline decided the change was safe. Next: what exactly gets shipped, and how it reaches customers." **Ask:** —

### Slide 13 — What gets shipped: more than the model file *(minutes 27–29)*
**Point:** the artefact is seven things, not one file. **Say it like this:** name the seven boxes quickly: code, configuration, a reference to the data (with its fingerprint, from Session 3), the trained model, the environment (exact library versions), documentation (the model card) and the test scenarios. Analogy: shipping only the `.pkl` file is like **moving house with only the sofa**: the sofa arrives, but there is nothing to sit it on, no instructions to assemble it, and nobody knows which room it belongs in. **Land:** "Shipping only the .pkl file is how the laptop-to-production failures of Session 3 happen." **Ask:** "Which of these seven did María's notebook have?" (Arguably only the model, and not even reproducibly.)

### Slide 14 — Four ways a model serves *(minutes 29–31)*
**Point:** how the model is used decides what can go wrong. **Say it like this:** **real-time**: one request, answered in milliseconds, like a **cash machine** (the fraud model; worry about speed and never being down); **batch**: a whole file on a schedule, like a **monthly bank statement** (the churn list every Monday at 6 a.m.; worry about the run finishing on time); **stream**: events scored as they flow, like **airport passport control** with a queue that never stops (the velocity features); **edge**: on the device itself, like a **smoke detector** that works without internet (a camera on a factory line). **Land:** "Today's activity is real-time: a card payment cannot wait." **Ask:** —

### Slide 15 — The artefact travels in a box: containers, then launch the poll *(minutes 31–33)*
**Point:** a container packs the model with its exact environment so it runs the same anywhere. **Say it like this:** the **shipping container** is the analogy: before it, every port loaded cargo its own way; after it, one standard box fits every ship, train and lorry. A software container does the same for a model: the code, the libraries and their exact versions, in one box that runs the same on a laptop or in the cloud. Compared with a virtual machine: a VM carries a whole operating system (a **house** on a lorry), a container carries only what the app needs (a **suitcase**), so it starts in seconds. Docker makes the box; Kubernetes runs thousands of them (after the break). Then **launch the chat poll** and leave it open during the demo on the next slide: "A model that passed all automated tests can be released to 100% of customers at once." AGREE or DISAGREE, one line why; "type it but don't press Enter until I say go". At the end of the demo, read two contrasting answers and **do not resolve**: it becomes Forum 3, Theme A, the rollback drill. For your Friday synthesis: tests tell you the model is not broken; they cannot tell you how customers, fraudsters or the business will react. **Land:** "Answer while I show you the box." **Ask:** the poll.

### Slide 16 — Demo: from the registry to a live endpoint, in four steps *(minutes 33–37)*
**Point:** the slide is the map of the demo: four cards (a model in the registry, a Dockerfile, a container running, scoring two customers); point to each card as you do the step, so the terminal never feels abstract. **Say it like this:** **Demo 2, about 4 minutes** (`MLOps_S05_Demo_Script.md`, section 3): show the box built last night from the Session 3 registry's **production** model (optionally its eight-line recipe, `cat registry_box/Dockerfile`), start it, check it's alive, send it two customers (answer `[0, 1]`: the loyal one stays, the at-risk one leaves), and stop it: "This is what 'deployed' means: a registry entry turned into a running service waiting for requests. And rollback is stopping this box and starting the previous one." Then read two answers from the poll. **Land:** "Passing the tests is necessary, not sufficient. That's what the next block is about." **Ask:** —

## Rollout: reaching customers without downtime (17–23)

### Slide 17 — Divider *(minute 35)*
**Point:** five strategies in eleven minutes, each drawn the same way (before, during, after), then a scorecard. **Say it like this:** "The pipeline said yes. Now: how many customers meet the new model on day one?" **Land:** —. **Ask:** —

### Slide 18 — Zero downtime, rollback, and the basic strategy *(minutes 35–37)*
**Point:** two definitions, and the strategy that ignores them. **Say it like this:** **zero downtime**: at no moment is the service down or answering wrongly because of the release; customers never notice. For card payments it is not optional: a minute without the model means every payment is either blocked or waved through. **Rollback**: going back to the previous version (model, code and configuration), which must still exist and be deployable in minutes. **Basic deployment**: replace everything at once, like **changing all the tyres of a car while it is driving**: fast and cheap, and for a moment everyone gets the untested version, or nothing. Fine for internal tools, test environments or a Sunday at 4 a.m. **Land:** "If you can't roll back in minutes, you don't have a rollback." **Ask:** —

### Slide 19 — Blue-green *(minutes 37–39)*
**Point:** two identical environments and one switch. **Say it like this:** one environment is live with v1 (here called green), a full copy (blue) gets v2 and is tested with no customers; when it is accepted, all traffic is switched over at once, and the old one stays ready as the rollback. Analogy: a **theatre with two identical stages**: the new set is built behind the curtain, and at the interval the audience is turned to face it; if it fails, they turn back. Pros: simple, rollback is flipping the switch back. Cons: two full production environments cost money, realistic test traffic is hard, keeping both truly identical is hard. (If someone has read that "blue" is usually the live one: the colours are only names; what matters is that one is live and one is waiting.) **Land:** "Zero downtime, if the switch is instant; but everyone meets v2 at the same moment." **Ask:** —

### Slide 20 — Shadow *(minutes 39–41)*
**Point:** the new model scores everything and nobody sees its answers. **Say it like this:** every real request is answered by v1; v2 scores the same request in the background and its answer is only written down; after enough requests you compare. Analogy: a **driving pupil with a dual-control instructor**: the pupil decides what they *would* do at every junction, but the instructor is the one who actually drives. Pros: v2 sees real data with zero customer risk; rollback is switching it off; proof of equivalence before anyone is affected. Cons: twice the compute; you learn what v2 *would have said*, not how customers or fraudsters react. **Land:** "IberBank's regulator will like this one: proof on real traffic before any customer is affected." **Ask:** —

### Slide 21 — Canary *(minutes 41–43)*
**Point:** a small slice of customers first, then more, then everyone. **Say it like this:** named after the **canary in the coal mine**: miners took a bird underground because it would react to gas before they did. A small share of traffic (1%, 5%, 10%) goes to v2 and is watched; if healthy, the share grows step by step until v1 is retired. Also like a **soft opening** of a restaurant for friends and family before the public. Pros: no second full environment, risk bounded by the slice, the lowest-risk way to reach real customers. Cons: two behaviours in production at once; the slice must be big enough to see problems and small enough to limit the damage; you need monitoring good enough to decide (Session 7). **Land:** "Shadow exposes nobody; canary exposes a few, on purpose, to learn how real customers react." **Ask:** —

### Slide 22 — A/B testing is not a canary *(minutes 43–45)*
**Point:** same picture (traffic split), different purpose: safe versus better. **Say it like this:** a **canary asks "is v2 safe?"**: it watches errors and speed and grows the slice when nothing breaks. An **A/B test asks "is v2 better?"**: two comparable groups chosen at random, one metric decided in advance, a decision after enough traffic. Analogy: a **clinical trial**: you decide before the trial what "works" means, and you don't stop the moment the first patient feels better. Three ingredients: **a metric** (fraud caught at a fixed false-positive rate), **a threshold** ("v2 wins if it catches 2 points more fraud with the same false positives"), **enough traffic** (so the difference is not luck; more than a busy afternoon; the statisticians set the number). **Land:** "Metric, threshold, enough traffic: decided before you start, or it's not a test." **Ask:** "What would be the wrong metric for a fraud model?" (Accuracy: blocking nothing scores 99.6%.) This is Forum 3, Q3.

### Slide 23 — The scorecard *(minutes 45–46)*
**Point:** the five strategies side by side, and how they combine. **Say it like this:** read the rows quickly and let the chat fill a gap or two: zero downtime, extra cost, customer risk, what you learn, rollback. Then the bottom line: strategies combine, **shadow first** (the regulator's proof), **then a canary**, with **an A/B rule inside it**. Like a **new medicine**: lab tests, then a small trial, then wider use, with the success measure written down first. **Land:** "That combination is today's activity." **Ask:** "Which column would a CFO read first?" (Extra cost.) Then the break.

## Serving at scale (25–28)

### Slide 25 — Divider *(minute 51)*
**Point:** seven minutes on what holds the model up when traffic arrives. **Say it like this:** answer the break question first: "Either the app slows down and falls over, or something adds capacity by itself. That something is today's next seven minutes." **Land:** —. **Ask:** —

### Slide 26 — Scaling *(minutes 51–53)*
**Point:** a bigger machine, more machines, or both, automatically. **Say it like this:** **vertical**: a bigger machine, like hiring **one faster cashier**: simple, but there is a fastest possible cashier, and they're expensive. **Horizontal**: more machines behind a **load balancer**, like **opening more tills** with someone directing customers to the shortest queue: no ceiling, more moving parts. **Autoscaling**: tills open and close by themselves; **scheduled** (we know the Black Friday rush is coming) or **dynamic** (when the queue gets long, open another; when it shrinks, close one). **Land:** "Elastic means you pay for the peak only during the peak." **Ask:** —

### Slide 27 — Kubernetes in one slide *(minutes 53–55)*
**Point:** Kubernetes is the manager of the boxes. **Say it like this:** first, 20 seconds of definition, because students have only heard the name once (slide 15): "Kubernetes is software, free and open source, originally from Google, that manages containers across many machines. The name is Greek for 'helmsman', which is why its logo is a ship's wheel; you'll also see it written 'K8s'." (One product: "Kubernetes *is*".) Then: with hundreds of containers on dozens of machines, someone must start the right ones at the right time, connect them, and replace the ones that fail, day and night. Kubernetes does that automatically. Analogy: an **orchestra conductor**, or a **port's container terminal**: Docker builds the containers; Kubernetes decides which ship, which crane and which berth, and reroutes when a crane breaks. Scalable means you *can* add machines; elastic means the system adds and removes them *by itself*. **Land:** "Docker makes the box; Kubernetes runs thousands of boxes." **Ask:** —

### Slide 28 — Serverless *(minutes 55–58)*
**Point:** pay for the seconds the model runs, and nothing else. **Say it like this:** three ways to host the endpoint: run your own web server (you own the machine and the patches), a cloud ML platform (SageMaker, Vertex AI, Azure ML, watsonx.ai host it for you), or **serverless functions**: you upload a function and the cloud runs it only when a request arrives. Analogy: **a taxi versus owning a car**: no parking, no insurance, you pay per trip; but you wait for it to arrive (a "cold start") and, if you travel all day every day, owning is cheaper. Fits: irregular traffic, simple models, no infrastructure team. Does not fit: strict latency, heavy models, constant high traffic: the fraud model. **Land:** "Serverless is perfect for the model nobody calls at night, and wrong for the one called 40 million times a month." **Ask:** —

### Slide 31 — Debrief *(minutes 76–86)*
**Point:** three rooms present, then the strong answer, then the closing line. **Say it like this:** pick three rooms with different plans if you can (one with shadow, one with canary only, one with blue-green). Then walk the table: **plan**: shadow for two to three weeks (the regulator's proof, inside the four-week budget), then a canary by channel, e-commerce first, 5% → 25% → 100%, with the A/B rule inside; not blue-green alone (no proof on real traffic, everyone switched at once), not basic (zero downtime). **A/B rule**: confirmed fraud caught per 1,000 flagged, at a false-positive rate no higher than v1's; v2 wins if at least 5% better; at least a full week including a weekend. **Rollback trigger**: false-positive rate 10% above v1's for an hour, or the review queue above 300 a day, or p95 latency above 150 ms; an automated monitor pages the on-call ML engineer; the canary shrinks to 0%. **Who signs**: product owner (each go), Risk & Compliance (the regulator's evidence), ML engineer (executes). Correct gently: blue-green alone; a metric with no threshold; "we'll decide the rollback when we see a problem". **Land:** "Every strategy is a way to make a mistake small. The pipeline decided the change was safe; the rollout decides how many customers find out if it wasn't." Say it slowly. **Ask:** —
